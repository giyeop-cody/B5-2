# 구현 회고

## 이해가 깊어진 부분

- 브라우저 요청은 한 함수에서 끝나는 것이 아니라 HTTP 경계, 업무 규칙, 저장소, 화면 표현을 차례로 통과한다.
- PRG는 단순한 페이지 이동이 아니라 변경 요청과 조회 요청을 분리하는 브라우저 흐름이다.
- SQLAlchemy Session은 객체를 보관하는 리스트가 아니라 트랜잭션과 객체 상태를 연결한다.
- DTO를 두면 템플릿이 DB 모델에 직접 기대는 범위를 줄일 수 있다.

## 선택한 설계

단일 Memo CRUD에서는 Repository가 각 작업의 commit을 담당하도록 단순화했다. 검증은 Service에 두고, Router는 성공·실패 결과를 템플릿 또는 redirect로 바꾼다. 없는 데이터는 학습용 SSR 흐름에 맞춰 목록과 안내 문구를 보여준다.

## 해결 과정에서 확인한 문제

- POST 결과를 바로 렌더링하면 새로고침으로 요청이 재전송될 수 있어 303 PRG를 적용했다.
- commit 실패 뒤 rollback하지 않으면 Session을 계속 사용할 수 없어 공통 commit 헬퍼에서 복구한다.
- 템플릿 엔진 API는 버전에 따라 호출 형식이 달라질 수 있어 의존성 범위와 실제 실행 테스트가 필요하다.
- 문서 예제도 코드와 함께 검증하지 않으면 경로·필드·상태 코드가 쉽게 어긋난다.

## 남은 한계와 다음 학습

현재 구조는 단일 모델과 단일 작업에 맞춰져 있다. 여러 저장 작업을 하나의 트랜잭션으로 묶는 Unit of Work, 실제 404 화면, CSRF 보호, 관계 로딩 전략, 마이그레이션 도구, 비동기 DB 접근은 다음 단계에서 비교할 주제다.
